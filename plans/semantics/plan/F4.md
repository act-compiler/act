# F4 Control register semantics across both generators

## What

- Fix the evaluation order of S5.4 as one definition: every expression of an issue reads the state before the issue, and updates and outputs take effect together at its end (Q1.1).
- act-oracle: move update emission after the outputs and make it a parallel assignment (instruction_codegen.py:162-181).
- act-backend: model state variables in the allocator as symbolic i64 variables threaded through the instruction stream, or keep the rejection with a coverage row.
- Front end: reject an initial value outside i64.
- Corpus: the `load` case of the oracle test (test_state.py:24-28) guards and writes at the same row.

## Benefits

- Closes H3 and H12; makes stateful ISAs usable by the backend.

## Caveats

- Backend state modelling is the largest single item and may stay rejected in v3 with a documented row.

## Fail points

- A start that depends on an update makes allocation order-dependent; the solver needs the instruction order, which the e-graph does not fix until extraction.

## Order and dependencies

- Depends on L (S5.4), F3.
- Feeds B, O, T.

## Verification

- A pointer-bump ISA (`@s.ptr = @s.ptr + @c.n`) runs the same trace in the oracle and compiles in the backend, or the backend names the feature it rejects.
