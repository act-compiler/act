# Panel 12, round 1, Fable

Lens: ML systems and PyTorch backend architect.
Code paths are relative to /home/user; plan paths are relative to /home/user/act.

### Q12.1

Position: option A, as three gated steps, and the front end never leaves Python.

1. The backend already has the shape of an MLIR pipeline on the wrong substrate: a 2,100-line Rust text reader for XLA HLO (act-backend/act_backend/generic/src/isel/initializer/parser.rs:17-50, plans/backend/plan/parser.md:4), egg saturation (generic/src/pipeline.rs:14), candidate text handed to a C++ allocator (pipeline.rs:249-253), and Python generators that emit Rust and C++ by template (act_backend/ir_egraph_rs_generator.py, act_backend/isel_applier_rs_generator.py, act_backend/malloc_act_malloc_cc_generator.py).
2. Decision 43 asks for native StableHLO, MLIR, and torch-mlir input; the plan stages that as B43 "detection now, readers staged" after B42's input specification (plans/roadmap/wave-4-7.md:27-28), so the first C++ step is a reader that parses StableHLO and HLO through MLIR and builds today's e-graph, gated by B3.
3. The reader consumes portable artifacts, because StableHLO guarantees compatibility only for them, 5 years backward and 2 years forward, while textual and bytecode forms "do not have compatibility guarantees" (https://openxla.org/stablehlo/compatibility); so B43's detection accepts a portable artifact and the backend pins one libStablehlo version, which satisfies decision 33.
4. Step two generates a TAIDL ISA dialect from the checked `Model`: one operation per selectable instruction (B13, plans/roadmap/wave-3.md:14), its attributes as the instruction's attributes, its region constraints as native constraints; PDLL gives patterns this form, where "Constraints may also be defined outside of PDLL, and registered natively within the C++ API" (https://mlir.llvm.org/docs/PDLL/).
5. The dialect is generated as C++ at generation time, not loaded at run time through IRDL, since a dialect using `irdl.c_pred` "cannot be registered at runtime, as it relies on C++ code" (https://mlir.llvm.org/docs/Dialects/IRDL/) and every region constraint is such a predicate; this keeps today's generate-then-build model (act-backend/README.md:94).
6. Step three moves saturation and extraction to the C++ e-graph of Q12.3; the allocator and cost are already C++ (generic/cpp/malloc, generic/cpp/cost), so after step three Rust is gone and Python remains only at generation time.
7. The front end stays Python because decision 41 allows a Python meta-DSL with few dependencies, and because the typed contract plans the hinge: "A serialized form is added at the second non-Python consumer" (plans/shared/interface.md:66); the C++ backend is that consumer, so the `Model` export is the only new front-end work.
8. Option B gives the backend nothing: no backend stage reads Python objects after U2 and U3 (interface.md:54-58), so a C++ front end would duplicate `check`, which decision 42 defines once.
9. Option C loses the gate: every structural step passes B3 by identical chosen assembly and `--log` files in B29's deterministic mode (plans/backend/plan/overhaul.md:5), and a one-shot rewrite has no intermediate to compare.
10. The MLIR dependency is shared, not new: fsim-lib's pass stage already builds MLIR and StableHLO static libraries at StableHLO 1.20.0 (plans/oracle/fsim/native-path.md:25, plans/oracle/fsim/architecture.md:68); IREE shows the layering, StableHLO input then Flow, Stream, HAL (https://iree.dev/developers/general/developer-overview/), and its plugin API shows a backend as dialects, input conversion, and HAL targets behind `onRegisterDialects` and `populateHALTargetBackends` (https://github.com/iree-org/iree/blob/main/compiler/src/iree/compiler/PluginAPI/README.md).
11. ACT does not become an IREE plugin: IREE's dynamic plugins must match "the host compiler's exact IREE and LLVM/MLIR revisions" (same README), which decision 33's released pins cannot follow, and decision 28 keeps dependencies few; the shape is borrowed, the dependency is not.

Confidence: high on backend first and on the front end staying Python; medium on the step order, since the ISA dialect may land before the reader if B13 lands early.

What would change my mind: a measured MLIR build cost that breaks released pins for act-backend, or evidence that the C++ reader cannot reproduce every message pinned by tests/test_reader.py.

### Q12.2

Position: option C, compile path first through torch.export to a StableHLO portable artifact, the eager device later as a test device over the generated oracle, and a PJRT plugin as the JAX door on the same compile entry.

1. The compile-path contract is small and out of tree: "A backend function has the contract `(gm: torch.fx.GraphModule, example_inputs: List[torch.Tensor]) -> Callable`", it is named through `register_backend` or the `torch_dynamo_backends` entry point group, and `aot_autograd` means "custom backends only need to support the core Aten opset" (https://docs.pytorch.org/docs/2.15/user_guide/torch_compiler/torch.compiler_custom_backends.html).
2. The ahead-of-time door is torch.export: `run_decompositions(decomp_table=None)` yields Core ATen, about 180 operators, the program "will error out when something untraceable is reached" instead of graph-breaking, and `torch.export.save` writes a `.pt2` zipfile (https://docs.pytorch.org/docs/2.15/user_guide/torch_compiler/export.html); the no-graph-break rule is decision 40's "invalid or outside the input specification" at the framework boundary.
3. Two converters exist from an `ExportedProgram`: torch-mlir's `export_and_import(f: Union[nn.Module, ExportedProgram], ..., output_type=...)` with a StableHLO output type (https://github.com/llvm/torch-mlir/blob/main/python/torch_mlir/fx.py), and `exported_program_to_stablehlo`, which saves "StableHLO portable bytecode artifacts which have complete forward and backward compatibility guarantees" (https://openxla.org/stablehlo/tutorials/pytorch-export); the second one ships from PyTorch/XLA, which is deprecated and archived on November 15, 2026 (https://docs.pytorch.org/xla/master/features/stablehlo.html), so the torch-mlir importer is the durable converter and the artifact is the handoff.
4. IREE is the precedent for both doors at once: iree-turbine "integrates into PyTorch as a custom backend for torch.compile" and exports ahead of time to an artifact (https://iree.dev/guides/ml-frameworks/pytorch/).
5. Portability across TAIDL accelerators comes from the generated backend, not from PyTorch: the same StableHLO reaches each generated compiler (act-backend/README.md:57), so the torch package carries no per-accelerator code and no fork.
6. Decision 40 inside the compile path: an op outside the input specification rejects the graph with a coded error (B42, wave-4-7.md:27); a candidate failure drops the candidate with a reason (plans/backend/plan/failures.md:26); the backend never falls back to CPU on its own, since that hides a rejection; partial delegation, where a partitioner tags the nodes it can lower and "Every subgraph will be sent to the preprocess part provided by the backend to be compiled as a binary blob" (https://docs.pytorch.org/executorch/stable/compiler-delegate-and-partitioner.html), is a later opt-in with the undelegated ops reported like the B46 exclusion report.
7. Testability: the compile path emits a kernel the generated oracle runs, which B3's behavioral step already does for every backend program (plans/backend/plan/architecture.md:38-39).
8. Option B first is wrong for ACT because an eager device needs a runtime ACT does not own: the accelerator guide's minimum set is `empty.memory_format`, `empty_strided`, `as_strided`, `_copy_from`, and friends, with guard, stream, event, and allocator, after which unsupported ops "automatically fall back to the CPU for execution" (https://docs.pytorch.org/docs/2.15/accelerator/operators.html, https://docs.pytorch.org/docs/2.15/accelerator/index.html); TAIDL describes the ISA, not a driver.
9. The eager device therefore comes later over the generated oracle, which gives PyTorch tests a device for every ISA specification, loaded through the `torch.backends` autoload entry point (https://docs.pytorch.org/docs/2.15/accelerator/autoload.html); the CPU fallback is blocklisted there, so an unsupported op errors as decision 40 wants.
10. The eager path also loses the whole-kernel view selection needs: PrivateUse1 dispatches one ATen op at a time, while the e-graph selects over the kernel (pipeline.rs:226-240).
11. Option D, worth naming: a PJRT plugin is a shared library exposing `GetPjrtApi`, found by JAX through the `jax_plugins` namespace (https://openxla.org/xla/pjrt/pjrt_integration), compiling StableHLO, the same input as step 2; fsim-lib already speaks the PJRT C API as a client (plans/oracle/fsim/native-path.md:22-23), so a plugin over the ACT compiler and the oracle reaches JAX with no new input format; it reaches PyTorch only through the deprecated PyTorch/XLA `DevicePlugin` (https://docs.pytorch.org/xla/release/r2.9/contribute/plugins.html), so it is the JAX door, not the PyTorch one, and the PJRT header pin "match the jaxlib version with the PJRT C API version" (pjrt_integration page) is the same pin fsim-lib carries.

Confidence: high on compile path first and torch-mlir as the converter; medium on the eager device over the oracle, whose value depends on per-op compile latency; medium on the PJRT plugin, which depends on the C++ oracle landing.

What would change my mind: a TAIDL target with a real runtime driver, which makes the eager device a product; or torch-mlir StableHLO coverage gaps on the owner's kernels, which would favor the HLO path through XLA as today.

### Q12.3

Position: option B, a standalone C++ library with its own term representation and an MLIR bridge, built in the order B31, B7, B6, B9, then the engine.

1. Decision 45 names the four features; the engine today provides them through egg's `Analysis` with a `panic!` on disagreement (generic/src/ir/egraph.rs:393-411), string payloads re-split per condition (egraph.rs:63-94), and number-keyed rules bound to three functions each (generic/src/isel/rewrites/applier.rs:9-58).
2. Option A is the eqsat dialect: `eqsat.eclass` groups e-nodes, congruence is kept by CSE over the whole graph, and e-matching is a custom `pdl_interp` interpreter that backtracks over every e-class member; its authors state "this flexibility may come at the expense of some performance" and "the pdl dialect cannot be used to match regions of operations" (https://arxiv.org/html/2505.09363v2).
3. Whole-graph CSE for congruence is the wrong fit for a search bounded at 10,000 nodes and one second (generic/src/lib.rs:18-20); egg's incremental rebuild is what the limits assume.
4. Option C has no candidate: egg and egglog are Rust, and egglog's integration points are the Rust crate, a Python binding, and WebAssembly, with no C or C++ API (https://github.com/egraphs-good/egglog); a Rust engine behind FFI is what decision 45 leaves.
5. E-matching: egglog's relational e-matching "is reduced to a query over the database" with generic join, and semi-naive evaluation "avoids redundant matches" for a 9.27x speedup on its math benchmark (https://arxiv.org/html/2304.04332v4); ACT's rule set is 10 IR-to-IR rules plus one per instruction (plans/backend/plan/isel.md:63), so the library starts with a backtracking matcher indexed by (op, class) and adds generic join only if B34's measurements show matching dominates.
6. Metadata: per-class typed data (shape, element type, constant-ness, folded value) computed in `make` as B7 and B9 plan (isel.md:30, isel.md:41), merged as a lattice meet with a coded fault instead of the panic, which plans/meeting/resolutions.md:11 already rules; this is egglog's merge-expression model, where egg "is artificially limited to a single type and a single analysis" (https://arxiv.org/html/2304.04332v4).
7. Preconditions: native C++ functions over variables bound by name and their class data, the B6 form (isel.md:51-52) and the PDLL native-constraint form; conditions take no engine type in their signature so one function serves egg and the C++ engine during migration.
8. Extraction keeps today's interface: enumerate repeat-free candidate instruction graphs under a limit (generic/src/isel/extractor/slow.rs:13-20) into the B2 typed struct; cost-aware extraction stays P6 (wave-4-7.md:131).
9. Migration runs both engines in B29's deterministic mode and passes when the chosen assembly and `--log` candidate files are identical per example (plans/backend/plan/search.md:23), with hash-map iteration order the named fail point (search.md:21); the C++ library therefore uses insertion-ordered containers only.
10. The MLIR bridge is thin: e-nodes carry the ISA dialect's op id and typed attributes; the bridge converts an MLIR function to e-nodes and an extracted candidate back to an MLIR region for the allocator, as the B2 struct does today in Rust (plans/backend/plan/architecture.md:25).

Confidence: high on B over A and C; medium on starting with a backtracking matcher rather than generic join.

What would change my mind on A: an upstream MLIR eqsat with incremental congruence and region matching; on the matcher: a B34 profile where matching exceeds allocation and cost on the examples.

### Q12.4

Position: the items join as later waves of the backend, shared, and oracle tracks, with design constraints placed on earlier items now and no new track.

1. Ownership: the backend track owns the C++ reader, the ISA dialect, the C++ e-graph, the torch compile path, and the PJRT plugin; the shared track owns the serialized `Model` and the toolchain pins; the oracle track owns the fsim-lib driver as O29's follow-ons; the act track owns the torch package release under decision 33.
2. The shared track adds U15, a versioned serialized `Model`, since interface.md:66 defers the serialized form to the second non-Python consumer; U15 depends on U2 and U3 (wave-2.md:45, wave-3.md:47); and U16, one third-party pin set for libStablehlo and the PJRT C API header, shared by backend and oracle, since fsim-lib pins both today (native-path.md:22-25).
3. The backend track adds, in order: B47 C++ MLIR reader for StableHLO portable artifacts, HLO, and torch-mlir input, depending on B42, B43, B3, and U16; B48 ISA dialect generated from the `Model`, depending on B13 and U15; B49 C++ e-graph behind a C ABI with the dual-engine gate, depending on B31, B7, B6, B9, B10, B35, and B29; B50 egg and the Rust crate deleted, depending on B49; B51 torch compile backend over torch-mlir and B47, depending on B47 and B42; B52 eager device over the generated oracle, depending on B51 and O35; B53 PJRT plugin over the compiler and the C++ oracle, depending on B47, O35, and U16.
4. The oracle track turns O29 (wave-3.md:28) into O34 to O37, the four steps of plans/oracle/fsim/native-path.md:32-41: a C++ emitter per instruction, `Pipeline::submit` and `sync` for `compile_and_load` and `execute`, debug print out of `custom_call`, and the pinned PJRT plugin; the fifth step, an interpreter, stays out under decision 28.
5. fsim-lib joins the platform through U16: its pass stage builds MLIR and StableHLO static libraries and serializes at StableHLO 1.20.0 (native-path.md:25, architecture.md:68), so B47 and O34 read and write one StableHLO version from one pin, released as decision 33 requires.
6. Earlier items change now by constraint, not by new work: U2 and U3 keep every `Model` field serializable with no Python-only type, which interface.md:56 already demands for ANTLR; B29 fixes candidate enumeration order as well as the search bound so a second engine can be compared; B31 and B2 define the typed payload as op id plus typed fields, which becomes B49's e-node (architecture.md:25); B6 writes preconditions over bound names with no egg type in the signature (isel.md:51-52); B43 detects StableHLO portable artifacts, not only HLO text; B7's shape rules stay generated from U4's table so a C++ copy is one more target (isel.md:31); O29's study adopts the state-to-state `@main` shape (plans/oracle/fsim/integration.md:43-49).
7. Waves: the constraints land inside the existing waves; U15 and U16 enter wave 7 with the other follow-ons (waves.md:28); B47, B48, and O34 to O37 form wave 8; B51 lands in wave 8 as a Python shim that writes the portable artifact B47 reads; B49 and B50 form wave 9, since B49 waits on the whole B31 to B35 chain and on wave 8's dialect; B52 and B53 land in wave 9 after O35 gives a C++ oracle to run on.
8. The waves rule holds, no item before a dependency (waves.md:9), and no M date is set for waves 8 and 9 before the M1 rebaseline (waves.md:15).

Confidence: medium-high on ownership and dependencies; medium on the wave split between 8 and 9.

What would change my mind: a B34 measurement that selection time is not the bottleneck, which would move B49 after B51 and B53; or an owner direction that the torch backend ships before the C++ e-graph.
