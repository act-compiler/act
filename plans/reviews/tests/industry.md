# Test suite plan review: industry comparison

An outside review of `plans/tests/` against mature conformance suites: the WebAssembly spec tests, Test262, the StableHLO interpreter tests, LLVM lit and FileCheck, SMT-LIB benchmarks, and riscv-arch-test with its Sail reference model.
Each finding names what to borrow and where the plan already does as well or better.

## Verdict

The plan has the shape every mature suite converged on: a corpus beside the spec (T5, T19), one verdict per case tied to a spec clause (T6), a per-implementation expectations table (T11), a reference-model comparison (T13), and a migration that deletes a test only when its fact lives on as a case.
Two things it does better than the references: `coverage.md` is rendered from `expectations.toml` (T21), where StableHLO's `status.md` is hand-maintained, and the no-undefined-behavior rule (owner decision 16) gives every run-time case a verdict, where StableHLO's guideline G5 skips such cases.
The gaps are in the case metadata, not the architecture: one `rejected` verdict stands where WebAssembly and Test262 distinguish the phase that rejects, the error is matched by prose regex where the references match a class or a prefix, coverage is reported per section where Test262 and riscv-arch-test report per clause or coverpoint, and the S8 reference library contradicts ruling R29.
No finding is a blocker.
The majors below are each a field in `case.toml` or a row kind in `expectations.toml`, so they fit into T5, T8, and T11 before any case is seeded, and cost little if done then.

## What the plan does better than the references

- Rendered coverage: `coverage.md` from `expectations.toml` (T21) cannot drift; StableHLO's `status.md` and riscv-arch-test's test lists are maintained by hand.
- Two implementations compared against each other and against a reference (T13 plus T8), where riscv-arch-test compares one DUT against Sail and StableHLO compares one interpreter against itself.
- Every run-time violation has a verdict (decision 16, R55); StableHLO guideline G5 excludes implementation-defined and undefined behavior from its tests.
- Property-based generation with shrunk counterexamples promoted to corpus cases (T9); riscv-arch-test's generator produces tests but does not feed failures back into a hand corpus.

## What the plan does worse

- Verdict granularity: one `rejected` where the references separate the rejecting phase (IN1).
- Match contract: prose regex where the references match a class, a prefix, or a clause id (IN2).
- Coverage granularity: section counts where the references report per clause or coverpoint (IN3).
- Case format: Python scripts where every reference is a text file any implementation can parse (IN15).
